# Agent Guidelines

## Development Notes

- Azure OpenAI supports both `AZURE_OPENAI_BASE_URL` (`.../openai/v1`, OpenAI-compatible with bearer auth and model in payload) and legacy `AZURE_OPENAI_ENDPOINT` + deployment URLs.
- Direct OpenAI support uses `OPENAI_API_KEY` and defaults to `gpt-5.5`; keep Azure deployment names separate from OpenAI model ids in registry decisions.
- Single model mode is controlled by `LEYLINE_ROUTER_ENABLED=false` plus `LEYLINE_FIXED_MODEL`; `LEYLINE_FIXED_PROVIDER` is optional when `ModelRegistry` can infer the provider.
- Dashboard API key overrides call provider `setApiKey()` hooks and can use Apple Keychain (`security` CLI), browser `localStorage`, or server memory; never return raw keys from dashboard APIs.
- `.env` API keys are explicit startup config and take precedence over Keychain-loaded keys; dashboard saves still update the running provider immediately.
- Azure runtime URL/model settings persist in Apple Keychain under `runtime-config:<ProviderName>` (same service as API keys); `.env` base URLs still take precedence on startup.
- For dashboard Keychain reads, `security find-generic-password` can exit nonzero when an item is simply missing; treat that as an unconfigured provider key, not Keychain unavailability.
- Normalize dashboard API payloads at the frontend boundary before rendering; provider/model/status fields can be absent in stats, logs, or runtime config responses.
- Dashboard request logs come from the singleton router logger via `/dashboard/stats`; log unavailable provider attempts too, preserve non-stream `response.usage`, keep logger tests isolated with `logger.clear()`, and make empty log states explicit in the UI.
- Logs panel empty states should replace the table entirely, not render alongside an empty table or placeholder rows; keep row error truncation display-only with full text available on hover.
- `/v1/chat/completions` must wait for dashboard/provider API key initialization before routing; browser `localStorage` keys only reach providers after the dashboard rehydrates them back through `/dashboard/api-keys`.
- `/v1/route` is always registered. Startup logs distinguish fixed model mode (`LEYLINE_ROUTER_ENABLED=false` + `LEYLINE_FIXED_MODEL`), classifier mode (`LEYLINE_ROUTER_MODEL` + `LEYLINE_OPENAI_BASE_URL`), and tier-default mode (no classifier). Dashboard Azure deployment selection does not enable fixed model mode — that requires env vars.
- Leyline validates client `Authorization` headers on `/v1/*` with default key `leyline` (`LEYLINE_CLIENT_API_KEY` / `LEYLINE_CLIENT_AUTH_ENABLED=false` to override). Provider keys live in Leyline env/dashboard.
- When the Janus external URL is enabled and `LEYLINE_CLIENT_API_KEY` is unset, Leyline generates a fresh random `ll-...` client API key per server process and prints it with the public URL.
- Dashboard and dashboard APIs are localhost-only; block requests with Cloudflare/proxy headers (`cf-connecting-ip`, `cf-ray`, `x-forwarded-for`) so the public tunnel only exposes `/v1/*`.
- Docker image builds need Node 22+ (`node:22-alpine`) because current Vite requires Node `20.19+` / `22.12+`; Node 18 fails with `CustomEvent is not defined`.
- Docker Hub README sync can return `Forbidden` even after Docker image push succeeds; keep that workflow step non-blocking unless Docker Hub token scopes are confirmed.
- On boot, Leyline uses Janus as the external URL supervisor unless `LEYLINE_TUNNEL_ENABLED=false`; Janus must expose the registered service at `LEYLINE_JANUS_BASE_URL`. Public URL is logged and returned in `/dashboard/stats` + `/dashboard/tunnel` for cloud clients that cannot reach localhost.
- Janus API access is authenticated when onboarding is enabled: `JanusTunnel` must reuse a stored credential, exchange a one-time pairing code, or capture the auto-started daemon's pairing code; persist the resulting Janus credential in the existing secret store and attach it to status, registration, refresh, and service discovery requests.
- JSON body limit defaults to `100mb` (`LEYLINE_BODY_LIMIT`); Express default is 100kb and causes `PayloadTooLargeError` on large chat/tool payloads. Run `npm start` (includes `prestart` tsc) so `dist/` matches source.
- Normalize `/v1/chat/completions` payloads at the server boundary (`normalizeCompletionRequest`) — Cursor may send multimodal `content` arrays or non-array `messages`; streaming failover uses `ensureMessageArray` to avoid `compressed.messages is not iterable`.
- Ollama is opt-in (`OLLAMA_ENABLED=true`). `canHandle` rejects registry cloud models (e.g. `gpt-5.5` → `openai`) and only accepts installed local tags. Without `LEYLINE_ROUTER_ENABLED=false`, Azure 400s still trigger multi-provider failover — pin Azure with fixed model mode.
- For Cursor + Azure, prefer Leyline → LiteLLM → Azure: `LEYLINE_ROUTER_ENABLED=false`, `LEYLINE_FIXED_PROVIDER=LiteLLM`, `LEYLINE_FIXED_MODEL=gpt-5.5`, then run `npm run litellm:azure` before `npm start`.
- LiteLLM is the Azure compatibility adapter for Cursor Agent request shapes (`azure/responses/<deployment>`). Avoid adding more Azure Chat Completions shims unless LiteLLM cannot cover a case.
- LiteLLM's Azure Responses transformer assumes function tools are nested chat-completions shape (`{ type: "function", function: { name } }`); normalize flat Cursor function tools before forwarding or it crashes with `TypeError: 'NoneType' object is not subscriptable`.
- LiteLLM cannot infer Azure deployment context/cost metadata from `azure/responses/<deployment>`; `start-litellm-azure.mjs` writes `model_info.base_model`, `model_info.max_input_tokens`, `model_info.max_tokens`, and `model_info.max_output_tokens`, enables pre-call checks, and sets `litellm_settings.cache: false`. Cursor + `gpt-5.5` default is `LITELLM_MAX_INPUT_TOKENS=128000` and `LITELLM_MAX_OUTPUT_TOKENS=16384`; lower these only to enforce a local budget. `LiteLLMProvider` has an optional rough JSON-size guard via `LEYLINE_LITELLM_PREFLIGHT_ENABLED=true`, but keep it off by default to match direct Azure behavior.
- Set `LITELLM_PAYLOAD_AUDIT=true` to log safe metadata-only inbound/outbound summaries for LiteLLM calls (message count, content char count, tool count, payload bytes, SHA-256 hashes) without logging prompt/tool contents. Use it to prove Leyline preserved the full input before comparing Azure `prompt_tokens`.
- LiteLLM streaming responses must be parsed as buffered SSE, not per transport chunk. Cursor-like tool-call deltas can split JSON across TCP chunks; dropping partial JSON makes Cursor miss tool calls or usage and can look like repeated tool loops.
- Azure 400 with payload `messages:[]` means normalization/sanitization dropped the conversation — router now runs `ensureMessageArray` before every provider call and rejects empty message arrays early; `normalizeCompletionRequest` also accepts Responses-style `input`.
- Cursor Agent sends flat tools (`tools[i].name`) and custom tools like `apply_patch`; Azure Chat Completions needs nested `tools[i].function.*` or `tools[i].custom.name`. Incomplete `custom.format: { type: "grammar" }` without `grammar.syntax/definition` becomes `{ type: "text" }` — otherwise Azure 400s with `tools[n].custom.format.grammar`.
- Leyline provider quotas (`LEYLINE_QUOTAS_ENABLED`) are **off by default**. When enabled, Azure defaults to 60 RPM which Cursor bursts exceed quickly — Cursor shows that as "User API Key Rate limit exceeded".
- `gpt-5.5` in the default registry maps to `openai`; Azure fixed-model setups need `LEYLINE_FIXED_PROVIDER=AzureOpenAI` when the deployment name matches an OpenAI model id.
- `ProviderRateLimiter` is the standalone pre-proxy scheduling layer for future RPM + TPM throttling. It queues per provider, uses rolling minute windows, logs delay events before sleeping, and exposes leases so provider-reported token usage can correct estimates after completion; keep it tested independently before wiring into `Router`.
- `ProviderRateLimiter` concurrency is intentionally per-provider: same-provider acquires serialize through that provider's queue, rejected acquires do not poison later queued work, and a sleeping Azure queue must not block OpenAI/LiteLLM queues.
- `ProviderRateLimiter` delay logging is best-effort and must not reject traffic if the logger fails. Re-read provider limits during scheduling loops so queued work can honor updated runtime configuration after it wakes.
- The Tauri wrapper owns sidecar startup and probes loopback `/healthz` before spawning Node. The Express API defaults to `127.0.0.1`; proxy-originated requests are allowlisted to authenticated `/v1/chat/completions`, `/v1/route`, and `/mcp`, while dashboard, static, health, readiness, and unknown routes stay internal. Janus supervises the external tunnel; Leyline does not launch Cloudflared directly.
- Janus external URL integration uses the stable namespace/alias contract (`PUT /api/namespaces/{namespace}/aliases/{alias}` and `GET .../endpoint`) rather than resolving legacy `/api/services/{id}` records. Default identity is `leyline/api`; only endpoint responses with `status: healthy` are accepted.
- Tauri dev must build the Node entrypoint before launching the dashboard, and the Rust sidecar must not force `LEYLINE_TUNNEL_ENABLED=false`; otherwise the sidecar cannot auto-start Janus. GUI-launched macOS apps also need common Homebrew/user bin directories added to Janus's PATH.
- Arcana Secret Bridge integration is read-through and read-only: configure `LEYLINE_ARCANA_<PROVIDER>_REF` (or `LEYLINE_ARCANA_SECRET_REFS` JSON), Arcana takes precedence over Keychain, and `.env` provider keys still take precedence over both. Resolution uses `arcana run --secret ... --env ... -- python3 -c ...`; the Arcana project policy must allow the reference, generated environment name, and runner.
- The dashboard exposes Arcana as a provider-key destination only when that provider has a configured Arcana reference. Selecting Arcana resolves the key read-only; `LEYLINE_ARCANA_OPENAI_API_URL_REF` also hydrates `OPENAI_BASE_URL` when no explicit URL is set.
- Packaged macOS launches from Finder do not inherit the shell's Node PATH; the Rust sidecar must pass through PATH plus `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, and `~/.volta/bin` before spawning `node`, or Tauri setup fails before the window opens.
- Tauri `setup` errors must not be propagated with `?`: on macOS, a sidecar spawn/entrypoint/readiness error returned from setup becomes an unhandled panic in Tao's `did_finish_launching` callback and aborts the GUI. Log the sidecar error, register the manager, and let the window launch so the underlying startup failure remains diagnosable.
- Crash reports from 2026-07-27 18:03:42 and 18:04:07 were both `SIGABRT` in `tao::platform_impl::platform::app_delegate::did_finish_launching`; they came from an older 1.3.3 bundle, not the current source. The installed `/Applications/Leyline.app` was built 2026-07-22 and direct launch proved its bundled Node was broken (`Library not loaded: @rpath/libnode.147.dylib`), while the 2026-07-27 generated bundle launched and kept its Node sidecar healthy. Same-version bundles make this stale-app mistake easy to miss: verify the generated path or copy it over `/Applications/Leyline.app` before testing.
- The Tauri window close event is intentionally prevented and hides the main window; the tray icon reopens/focuses it, while the tray menu's explicit `Quit Leyline` action calls `app.exit(0)` so the sidecar is stopped by the existing `RunEvent::Exit` handler. The tray requires the Tauri `tray-icon` feature, a dedicated transparent monochrome `src-tauri/icons/tray.png`, and `icon_as_template(true)` on macOS; the full opaque wordmark app icon is not a suitable status-bar image.
- 2026-08-04 verification: `npm run tauri:build -- --bundles app` rebuilt successfully, and installing the generated `.app` over `/Applications/Leyline.app` produced matching binary/resource hashes. A Finder-style launch spawned `/opt/homebrew/bin/node` with the bundled `_up_/dist/index.js`; `/healthz` and `/readyz` both returned 200. If users still see no API, they are likely launching a stale copy or a different bundle path.
- 2026-08-04 follow-up: the local API can be healthy while the public API is unavailable. The current `.env` and bundled `.env` explicitly set `LEYLINE_TUNNEL_ENABLED=false`, `/dashboard/tunnel` reports `disabled`, `janus` is not installed, and port 8088 is closed. Enabling the public URL requires installing/configuring Janus and rebuilding the bundle so its copied `.env` changes.
- 2026-08-04 desktop networking: Docker's `oasis-cognition-oasis-ui-1` publishes `*:3000`; Tauri WebKit reached that nginx listener while shell IPv4 curl reached Leyline's narrower `127.0.0.1:3000` listener, leaving the dashboard stuck on “Waiting for Leyline API…”. Desktop Leyline now uses free port `3417`, and `sidecar.rs` must pass its selected port as `PORT` to Node; changing only the Rust probe port leaves Node on its config default.
- 2026-08-04 blank dashboard diagnosis: the packaged WebKit window was white because `App()` read `localStorageAvailable` while evaluating `savedPersistenceMode` before the `const` declaration executed, causing a JavaScript temporal-dead-zone `ReferenceError` before React mounted. Keep hook-derived values used by render-time expressions declared before those expressions.
